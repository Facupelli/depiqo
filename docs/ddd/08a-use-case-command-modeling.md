# 08a - Use Case and Command Modeling

## Purpose

This document turns the main flows from Step 5 into concrete actions.

Each use case describes:

- who triggers it;
- what input data it needs;
- which external context data it needs;
- which invariants it enforces;
- which state changes it performs;
- which events/results it produces;
- which failure cases must be handled.

This document does not define controllers, database schema, or implementation classes yet.

---

# Use Case: Create WhatsApp-style Pending Rental

## Trigger

A rental customer completes the lightweight customer catalog flow and chooses to send the generated WhatsApp message to the tenant.

## Who triggers it

Rental Customer.

## Input data

Tenant id.

Branch id.

Rental period.

Selected equipment types.

Selected combos.

Rental customer contact data.

Estimated/quoted price if shown.

Order source/mode = WhatsApp-style.

## External context data needed

Tenant Management:
Validate tenant, branch, product mode, branch schedule, pickup/return slots, timezone, and whether WhatsApp-style flow is enabled.

Catalog:
Validate selected equipment types and combos are visible/rentable for the tenant and branch.

Catalog:
Resolve combo definitions if combos were selected.

Pricing:
Calculate estimated/quoted price if price is shown in the flow.

## Invariants enforced

A Pending Rental must belong to one tenant.

A Pending Rental must belong to one branch.

A Pending Rental must have one rental period.

A Pending Rental must contain at least one selected equipment type or selected combo.

Selected catalog items must be visible/rentable for the selected tenant and branch.

Selected combos must be valid catalog-visible combos.

A Pending Rental must not assign assets.

A Pending Rental must not block assets.

A Pending Rental must not be Confirmed.

The WhatsApp message is generated by the system but manually sent by the customer.

## State changes

Create Rental with status Pending.

Store selected branch reference.

Store rental period.

Store rental customer contact/reference/snapshot.

Store selected equipment type references/snapshots.

Store selected combo references/snapshots if any.

Store source/mode as WhatsApp-style.

Store estimated/quoted price snapshot if shown.

Do not create assigned assets.

Do not create asset blocks.

## Events produced

Pending Rental Created.

WhatsApp Message Generated, if tracked.

## Result

Pending Rental id.

Generated WhatsApp message data.

## Failure cases

Invalid tenant.

Invalid branch.

WhatsApp-style flow is not enabled.

Invalid rental period.

Invalid pickup/return slot.

Selected equipment type is not visible/rentable.

Selected combo is invalid, inactive, or not visible/rentable.

Missing rental customer contact data.

Pricing calculation fails, if price is required.

Pending Rental could not be saved.

# Use Case: Confirm Rental

## Trigger

Tenant staff clicks Confirm on a Pending or Draft Rental.

## Who triggers it

Tenant User.

## Input data

Tenant id.

Tenant user id.

Rental id.

Optional confirmation command metadata.

## External context data needed

Tenant Management:
Validate tenant user permissions, tenant configuration, selected branch, branch schedule, pickup/return slots, timezone, and product mode.

Catalog:
Validate selected equipment types and combos are still rentable.

Catalog:
Resolve combo definitions and expand selected combos into equipment demand.

Pricing:
Calculate or validate price and return price breakdown.

Asset Inventory:
Find eligible physical asset candidates by equipment type, branch, condition, ownership, and active status.

## Invariants enforced

The Rental must belong to the tenant.

The Tenant User must be allowed to confirm the Rental.

The Rental must be Pending or Draft.

The Rental must belong to one branch.

The Rental must have one valid rental period.

The Rental must contain at least one selected equipment type or selected combo.

Selected equipment types must still be rentable.

Selected combos must still be rentable.

Selected combos must be preserved as selected combos, even though they are expanded into equipment demand.

Combo availability is all-or-nothing.

Equipment demand from individual equipment and combos must be aggregated.

A Confirmed Rental must have assigned equipment assets.

A Confirmed Rental must have equipment asset blocks.

The same physical asset must not be blocked for overlapping rental periods.

The confirmed price snapshot must be preserved.

If validation, pricing, asset assignment, or asset blocking fails, the Rental must not become Confirmed.

## State changes

Store confirmed price snapshot.

Store price breakdown snapshot.

Assign equipment asset references.

Create equipment asset blocks.

Change Rental status to Confirmed.

Preserve selected branch reference.

Preserve rental period.

Preserve selected equipment and combo snapshots if needed.

## Events produced

Rental Confirmed.

Equipment Asset Blocks Created.

## Result

Confirmed Rental id.

Confirmed price snapshot.

Assigned equipment assets.

Equipment asset blocks.

## Failure cases

Rental not found.

Rental does not belong to tenant.

Tenant user lacks permission.

Rental is not Pending or Draft.

Invalid branch.

Invalid rental period.

Invalid pickup/return slot.

Selected catalog item is no longer rentable.

Selected combo is no longer valid.

Pricing calculation fails.

No complete asset assignment can satisfy the requested equipment demand.

One or more required assets cannot be blocked.

Concurrent confirmation/edit created conflicting asset blocks.

Rental could not be persisted as Confirmed.

# Use Case: Edit Confirmed Rental

## Trigger

Tenant staff edits a Confirmed Rental before pickup or delivery.

## Who triggers it

Tenant User.

## Input data

Tenant id.

Tenant user id.

Rental id.

Requested changes.

Possible changes include rental period, selected equipment types, selected combos, quantities, price adjustments, branch if allowed, customer data, notes, or other editable fields.

## External context data needed

Tenant Management:
Validate permissions, tenant configuration, selected branch, pickup/return slots, timezone, and product mode.

Catalog:
Validate changed equipment types and combos.

Catalog:
Resolve combo definitions and expand selected combos into equipment demand.

Pricing:
Recalculate or validate price and return price breakdown if the edit affects price.

Asset Inventory:
Find eligible replacement/additional asset candidates if the edit affects equipment demand, rental period, or branch.

## Invariants enforced

The Rental must belong to the tenant.

The Tenant User must be allowed to edit the Rental.

The Rental must be Confirmed.

Confirmed means reserved, not final.

A signed contract does not automatically make the Rental immutable.

If the edit changes rental period, equipment, combos, quantities, or branch, availability must be revalidated.

If the edit changes equipment demand, asset assignments and asset blocks must be updated consistently.

Combos can be added or removed from a Rental, but their contents cannot be edited inside the Rental.

A selected combo cannot be partially fulfilled.

Equipment demand from individual equipment and combos must be aggregated.

If the edit changes price, the price snapshot must be rewritten.

The Rental must not end in a state where period, items, price snapshot, assigned assets, and asset blocks disagree.

If the edited state cannot be fully satisfied, the confirmed Rental should remain unchanged.

## State changes

Update Rental items if changed.

Update selected combo references/snapshots if changed.

Update rental period if changed.

Update selected branch reference if changed and allowed.

Update confirmed price snapshot if changed.

Update price breakdown snapshot if changed.

Release old equipment asset blocks if no longer needed.

Assign new equipment asset references if needed.

Create new equipment asset blocks if needed.

Preserve consistency between Rental items, period, price snapshot, assigned assets, and blocks.

## Events produced

Confirmed Rental Edited.

Asset Blocks Released, if old blocks were released.

Equipment Asset Blocks Created, if new blocks were created.

## Result

Updated Confirmed Rental.

Updated price snapshot if changed.

Updated assigned equipment assets if changed.

Updated equipment asset blocks if changed.

## Failure cases

Rental not found.

Rental does not belong to tenant.

Tenant user lacks permission.

Rental is not Confirmed.

Rental is already Completed or Cancelled.

Edit is not allowed for the current Rental state.

Invalid branch or branch change not allowed.

Invalid rental period.

Invalid pickup/return slot.

Changed equipment type is not rentable.

Changed combo is invalid or not rentable.

Pricing recalculation fails.

New requested equipment demand cannot be satisfied.

Required replacement assets cannot be blocked.

Concurrent edit creates conflicting asset blocks.

Persistence fails.

# Use Case: Prepare Rental

## Trigger

Tenant staff starts preparation for a Confirmed Rental, reviews suggested accessories, and confirms selected accessories.

## Who triggers it

Tenant User.

## Input data

Tenant id.

Tenant user id.

Rental id.

Selected accessory types.

Selected accessory quantities.

Optional preparation notes.

## External context data needed

Tenant Management:
Validate permissions, tenant configuration, selected branch, and product mode.

Catalog:
Get compatible/default accessories for the Rental's equipment demand.

Asset Inventory:
Find eligible accessory asset candidates by accessory type, branch, condition, ownership, and active status.

## Invariants enforced

The Rental must belong to the tenant.

The Tenant User must be allowed to prepare the Rental.

The Rental must be Confirmed.

The Rental must not be Cancelled or Completed.

Preparation should happen before contract signing because accessories are detailed in the contract.

Accessories are optional.

Tenant staff can accept default accessories, reduce quantities, remove accessories, or select zero accessories.

Unavailable accessories do not automatically cancel the Rental.

The Rental can continue with zero accessories.

Only available accessory assets can be assigned and blocked.

The same physical accessory asset must not be blocked for overlapping rental periods.

If no accessories are selected, no accessory assets are assigned or blocked.

Preparation state, selected accessories, assigned accessory assets, and accessory blocks must remain consistent.

## State changes

Start or update preparation state.

Store selected accessory quantities.

Assign accessory asset references if accessories are selected.

Create accessory asset blocks if accessories are selected.

Mark Rental as Prepared.

If zero accessories are selected, mark Rental as Prepared with zero accessories and create no accessory blocks.

## Events produced

Preparation Started, if this is the first preparation action.

Accessories Reviewed.

Accessory Asset Blocks Created, if accessories were blocked.

Rental Prepared.

## Result

Prepared Rental.

Final selected accessories.

Assigned accessory assets if any.

Accessory asset blocks if any.

## Failure cases

Rental not found.

Rental does not belong to tenant.

Tenant user lacks permission.

Rental is not Confirmed.

Rental is Cancelled or Completed.

Selected accessory type is not compatible.

Selected accessory quantity is invalid.

Requested accessory assets are unavailable.

Accessory asset blocks conflict with another Rental.

Preparation could not be persisted.

# Use Case: Generate / Request Contract Signing

## Trigger

Tenant staff requests contract generation or signing for a Confirmed or Prepared Rental.

## Who triggers it

Tenant User.

## Input data

Tenant id.

Tenant user id.

Rental id.

Contract template id, if configurable.

Signer/customer data, if not already available from the Rental snapshot.

Optional message or signing metadata.

## External context data needed

Rental Commitment:
Get confirmed/prepared Rental details, rental period, selected branch, rental customer snapshot, selected equipment, selected combos, assigned assets, selected accessories, and price snapshot.

Tenant Management:
Validate tenant user permissions and tenant contract configuration.

Object storage / platform storage:
Store generated contract document if needed.

## Invariants enforced

The Tenant User must be allowed to request contract generation/signing.

The Rental must belong to the tenant.

The Rental must be Confirmed or Prepared according to tenant rules.

Contract generation should use stable Rental snapshots, not live mutable catalog/pricing data.

If accessories are required in the contract, the Rental should be Prepared before contract generation/signing.

Contract signing does not automatically make the Rental immutable.

If the Rental changes after contract generation/signing, re-signing may be required.

Contract generation/signing state must not control Rental confirmation.

## State changes

Create contract document/reference.

Create signing request.

Store signing request status.

Store signer/customer details used for the contract.

Store generated document reference if applicable.

## Events produced

Contract Generated.

Contract Signing Requested.

## Result

Contract id.

Contract document reference.

Signing request status.

Signing URL or signing instructions if applicable.

## Failure cases

Rental not found.

Rental does not belong to tenant.

Tenant user lacks permission.

Rental is not in a valid state for contract generation.

Tenant contract configuration is missing or invalid.

Required Rental data is missing.

Rental is not Prepared but tenant rules require preparation before contract generation.

Document generation fails.

Object storage upload fails.

Signing provider request fails.

Contract state could not be persisted.
